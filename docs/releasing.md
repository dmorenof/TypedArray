# Release process

Stable releases are always made from `master`. Do not tag an unreviewed commit on `develop`.

1. Merge tested changes from `develop` into `master` through a reviewed pull request.
2. Check that every required CI job passes on `master`, that the changelog describes user-facing changes, and that the PHP minimum version and public API are consistent with SemVer.
3. Select **Actions → Release → Run workflow**, choose the `master` branch, and enter a new SemVer version (without `v`, e.g. `1.1.0` for the proposed compatible update). Do not reuse a published tag.
4. The workflow runs the entire PHP test matrix and Composer validation before creating an annotated GitHub release and matching Git tag.
5. Git tags are consumed automatically by Packagist when the repository's package hook is enabled. Check Packagist separately after the release: the workflow itself does **not** upload any artifact to Composer.
6. Verify `composer require <package-name>:<version>` using an isolated consumer project.

## Controls to configure in GitHub

Enable branch protection/rulesets for `master` and `develop`: require pull requests and successful CI checks; restrict force pushes and branch deletion; consider required review. Add a protected GitHub environment called `release` and require reviewer approval for the publish job if your plan supports it.

The workflow requests write access only in the final release job; checks use read-only permissions. A manual release must still not be considered proof of publication on Packagist until the new package version appears there.

## Proposed package rename

The new name `php-typed-array/php-typed-array` has been staged in the development Composer metadata, but has **not** been published. The preferred repository URL remains `dmorenof/php-typed-array` after a GitHub rename. Confirm Packagist availability and ownership, rename the GitHub repository, verify the new URL in Composer and documentation, register the new package, and then mark the old package as abandoned with a replacement pointer **only after the new stable release is available**. **Do not** delete the old package or old tags, as existing consumers may still depend on them.

## Package identity and consumer compatibility checkpoint

`master` currently publishes `typedarray/typedarray` **1.0.2**. The proposed new Composer identity `php-typed-array/php-typed-array` exists only in `develop` and must not be advertised as installable before Packagist registration and a verified stable release. The GitHub repository is still `dmorenof/TypedArray` until it is explicitly renamed.

### Existing known consumers

- `dmorenof/casafari-sdk` depends on `typedarray/typedarray: ^1.0`, extends `\\TypedArray\\TypedArray` through `CasafariSDK\\Core\\TypedArray`, and customizes `__toString()` and access to the protected expected type.
- `dmorenof/sdk-runtime` depends on `typedarray/typedarray: ^1.0`.
- `dmorenof/sdk-generator` emits SDKs that use typed collections and the existing published package, directly or through the runtime. Confirm the emitted dependency metadata before switching its package identity.

Keep `TypedArray\\` and the subclassing surface stable. Static source review indicates the new code retains these APIs; it does **not** replace running the consumers' integration suites.

### Replacement strategy (staged only)

The proposed new package declares:

```json
"replace": {
  "typedarray/typedarray": "self.version"
}
```

Composer can then satisfy a compatible dependency on the old name using the new package at the **same version number**, without loading both implementations of the `TypedArray\\` classes. For example, a new `1.1.0` release would satisfy existing `^1.0` constraints but not an exact `1.0.2` constraint. Do not use `*` as the replacement range. This does **not** automatically migrate projects that request only the old name; they still need to opt in to the replacement.

Before a release:
1. Verify Packagist registration is actually available to the publishing account. An absent public search result is not proof of name ownership.
2. Rename the GitHub repository if desired, then update all GitHub URLs, CI badges, Composer support links, and release documentation.
3. Confirm the new package's real published metadata comes from the correct default branch and version tag; earlier tags belong to the old identity.
4. In isolated Composer consumer projects, verify both:
   - a direct dependency on the new package and an existing `^1.0` consumer such as `dmorenof/casafari-sdk`;
   - an SDK generated by `sdk-generator` using the published package and real `sdk-runtime`.
5. Verify that `composer show` and the lock file resolve **one** implementation of the `TypedArray\\` namespace, and run the consumers' PHPUnit suites.
6. Keep `typedarray/typedarray` available until the new stable release is installable and the dependent SDK migration has been exercised. Only then consider marking it abandoned with a replacement pointer.

The repository/package rename is a **publication decision** and is not implied by a green TypedArray unit-test run.
